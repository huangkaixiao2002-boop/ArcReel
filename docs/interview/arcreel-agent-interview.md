# ArcReel Agent 开发面试题与项目化回答

这份文档用于准备 Agent 开发、AI 应用后端、LLM 应用工程和全栈 Agent 平台岗位面试。回答重点放在场景、技术思路、设计原因和异常处理，不要求面试官查看代码。回答中的项目事实来自 ArcReel 当前实现；涉及“我负责”的表述，要根据自己的真实职责替换，避免把团队代码说成个人独立完成。

## 1. 面试开场

### 60 秒项目介绍

> ArcReel 是一个开源、自托管的 AI 视频创作平台，目标是把小说、剧本或创作构想转换成可以继续编辑的短视频生产资料。用户先提供文本或素材，系统经过内容分析、角色和场景资产整理、分集剧本、分镜和宫格设计，再调用图片、视频、音频和 TTS 供应商生成素材，最后合成成片或导出剪映草稿。
>
> 技术上项目分成前端交互层、后端 Agent Runtime 和领域服务层。前端负责项目编辑和实时反馈，后端负责会话、SSE 和工具调用，领域服务负责项目、资产、生成队列、供应商、账单和数据库。Agent 不是直接改数据库或生成任意 JSON，而是由主 Agent 做理解和编排，聚焦子 Agent 做局部推理，确定性操作通过 MCP 工具和后端服务执行。
>
> 这个项目真正需要解决的是长流程和异步状态的一致性。Agent 会话、SSE、远程供应商任务、数据库、文件系统和费用账本都可能在不同时间成功或失败，所以系统提供了会话串行化、持久化任务、供应商任务 ID、重启恢复、批量准入、幂等账单和项目版本历史。

### 项目亮点

> ArcReel 最大的亮点，是把不可控的 Agent 调用做成了可审核、可恢复、可计费、可继续编辑的生产流水线。模型负责理解和编排，子 Agent 负责局部推理，MCP 和后端服务负责确定性执行，用户在关键节点可以确认、修改、重做和回滚。

这个亮点可以继续落到四个具体实现上：

- 会话层用一个专属 Actor 串行持有 SDK 客户端，避免同一个会话被多个协程同时操作。
- 实时事件使用有限队列和背压策略，关键消息尽量保留，丢失的增量消息通过快照重新对齐。
- 生成任务持久化本地状态和供应商远程 task id，进程重启后继续查询，不把“前端断开”误判成“生成失败”。
- 费用记录采用 `pending → settled/failed/cancelled` 生命周期，恢复任务只结算原有 pending 调用，避免重复扣费。

### 整个项目最难的部分

> 整个项目最难的不是 Prompt，而是跨多个异步状态系统保证一致性。Claude Agent 会话、SSE 事件流、供应商远程任务、数据库、文件系统和费用账本都可能在不同时间失败。比如供应商任务已经提交，但前端 SSE 断开时，系统不能简单标记失败并重试，否则可能重复生成和重复扣费。ArcReel 通过 `SessionActor`、事件日志、持久化任务、供应商任务 ID、重启恢复、幂等账本和版本历史把这些状态连接起来。

面试中最好补一个具体场景：

> 假设视频供应商已经返回远程任务 ID，但浏览器此时断网。服务端仍然把任务和远程 ID 写入数据库，SSE 只是展示通道，不是事实来源。浏览器重连后先拉快照和任务状态，worker 继续轮询远程任务；如果最后成功，账本只会对原来的 pending 调用结算一次。

## 2. 项目与业务设计

### 题目 1：ArcReel 解决了什么问题？用户为什么需要 Agent？

**面试官想考什么：** 是否理解业务目标，而不是只会讲模型和框架。

**推荐回答：**

> ArcReel 解决的是“从创意到可编辑视频资产”的长链路问题。传统工具往往要求用户分别写剧本、做角色设定、画分镜、生成素材、配音和剪辑，步骤之间容易失去上下文。ArcReel 把这些步骤组织成一个项目级工作流，让用户可以从小说、剧本或创作构想开始，逐步得到角色、场景、道具、分集剧本、分镜、图片、视频和音频资产。
>
> Agent 的价值不是替用户一次性生成一个黑盒视频，而是理解当前项目状态，判断下一阶段缺什么，调用合适工具推进，并在高风险或高成本节点停下来让用户确认。这样用户可以修改角色、重做某个镜头、回滚某个版本，而不是只能接受一次生成结果。

**项目里的做法与原因：**

- 产品链路是“内容分析 → 角色/场景/道具 → 分集剧本 → 分镜/宫格 → 图片/视频/TTS → 成片或剪映草稿”。
- Agent 的 Skill、子 Agent 和系统提示与开发辅助配置分离，保证运行时规则稳定、可审计。
- 项目、资产、任务、费用和版本信息由领域服务管理，模型只能通过服务和 MCP 工具接触这些确定性能力。

**可能追问：** 为什么不做成固定 DAG？

**追问回答：**

> 固定 DAG 适合输入和分支都稳定的任务，但创作过程经常会出现“先改角色再重做镜头”“只补一集”“用户上传参考图后重新审核”等分支。ArcReel 让 Agent 根据项目状态选择下一步，同时把真正需要一致性的读写、任务创建、合成和导出放在确定性服务里，兼顾了灵活性和可控性。

### 题目 2：请用一条链路说明用户发出一句话后系统怎么工作？

**推荐回答：**

> 用户消息进入 FastAPI 的 Agent 会话接口后，`SessionManager` 找到或创建项目会话。会话由 `SessionActor` 持有 Claude SDK 客户端，消息进入 actor 的命令队列。SDK 返回的原始 frame 由 `_MessagePump` 持续读取并解析，`SessionEntryPipeline` 将 frame 归一化成增量草稿、事件日志和终态结果，再通过 `SseChannel` 广播给前端。
>
> 主 Agent 读取项目状态，判断当前工作流阶段；需要局部推理时调用 Skill 或子 Agent；需要读写项目、创建生成任务、查询状态、合成或导出时调用 MCP 工具。MCP 工具通过 `ProjectScope`、`CallerContext` 和 `Services.defaults(...)` 访问项目服务。若生成任务涉及外部供应商，队列和 worker 负责异步提交、轮询、保存输出和结算费用。前端收到事件后更新 Zustand store，写操作完成后通过统一的 `refreshProject` 拉取权威快照。

**项目里的做法与原因：**

1. 会话管理器负责创建、恢复、关闭和淘汰会话。
2. 会话 Actor 串行处理 SDK 命令和消息流。
3. 消息管道把 SDK frame 转成增量草稿、事件日志和终态结果。
4. 会话流和项目事件流共用广播、订阅、心跳和背压机制。
5. 工具使用统一声明和项目作用域，内置宿主与远程宿主保持同一套契约。
6. 生成任务按媒体类型和供应商容量进入不同执行 lane，由 worker 异步执行。

### 题目 3：你会如何描述自己在项目中的职责？

**推荐回答：**

先按真实职责把下面的空白替换成自己的工作范围和结果，不要把团队工作描述成个人独立完成。

> 我主要负责 ______。我的工作边界是从 ______ 进入，到 ______ 结束。例如在 Agent Runtime 方向，我负责会话生命周期、SDK frame 处理、工具调用和 SSE 事件交付；在生成链路方向，我负责任务入队、异步供应商状态、恢复和计费；在前端方向，我负责项目状态、事件订阅和写入后的刷新一致性。除了代码，我还会为每个边界补测试，重点覆盖重连、取消、恢复、重复提交和失败结算。
>
> 我不会把整个 ArcReel 说成自己独立完成，而是明确哪些部分由我主导、哪些是和团队共同设计的。面试时我会用一个具体场景、一次故障或一个边界用例说明自己的贡献。

**项目里的做法与原因：**

- 如果负责会话方向，可以说明自己如何保证一个会话内的命令串行、消息流不丢终态，以及断线后如何恢复。
- 如果负责生成方向，可以说明自己如何把任务、供应商远程任务、重试和计费串起来。
- 如果负责前端方向，可以说明自己如何把刷新请求合并、取消旧项目请求，并在写入后重新拉取权威快照。

### 题目 4：Agent 项目最容易失控的地方是什么？ArcReel 如何限制它？

**推荐回答：**

> Agent 最容易失控的地方是让模型直接承担确定性执行：例如自由生成 JSON、直接写项目文件、直接拼 SQL、直接调用供应商 SDK。这样一旦字段缺失、路径错误或重试，就会产生不可恢复的数据问题。
>
> ArcReel 的做法是把职责拆开：主 Agent 负责理解和编排，子 Agent 负责聚焦推理，MCP 工具和服务层负责校验、读写、创建任务、查询状态、合成和导出。Agent 可以提出“要做什么”，但最终由工具参数 schema、项目作用域、访问策略、任务队列和账本完成“能不能做、怎么落库、失败怎么恢复”。

**项目里的做法与原因：**

- 工具参数和返回结构集中声明，所有入口都从同一份契约生成，避免不同宿主出现同名工具参数不一致。
- 每个项目会话创建隔离的工具服务，并注入项目作用域、调用者上下文和领域服务；这样模型只能操作当前项目，不能直接访问任意路径或数据库。
- Agent 不能通过工具绕过服务层直接写数据库，也不能直接决定费用结算。
- 文件写入受 `AgentAccessPolicy` 约束；生成素材由主进程服务和任务队列写入受保护目录。

## 3. Agent 架构与工具设计

### 题目 5：为什么采用“主 Agent + Skill + 子 Agent + MCP”的结构？

**推荐回答：**

> 主 Agent 负责全局上下文和流程编排，Skill 负责把一类工作变成可复用的操作规范，子 Agent 负责分集规划、剧本规范化、资产生成、审图、审片等局部任务，MCP 工具负责确定性执行。这样既不会把所有逻辑塞进一个超长 Prompt，也不会让每个子 Agent 都拥有完整项目权限。
>
> 子 Agent 返回的是局部结论或结构化中间结果，主 Agent 再根据项目状态决定是否继续、重试、让用户确认或进入下一阶段。涉及文件和数据库的动作仍然通过 MCP 和服务层完成，因此模型输出不会直接成为最终事实。

**项目里的做法与原因：**

- 运行时 Agent 配置与开发辅助配置分离，避免开发环境规则意外进入生产会话。
- 聚焦子 Agent 的职责按工作流阶段拆分，避免一个 Agent 同时承担剧本、画面审核和供应商调度。
- 会话级工具服务把异步生成封装成可追踪的任务操作，模型只需要提出生成意图，不需要自己实现轮询和重试。
- 子 Agent 输出局部结论或结构化中间结果，主 Agent 根据项目状态决定继续、重试或请求确认，避免局部推理直接改写最终事实。

### 题目 6：MCP 工具和普通函数调用有什么区别？项目为什么使用 MCP？

**推荐回答：**

> 在这个项目里，MCP 不只是把 Python 函数暴露给模型，而是把工具能力、参数约束、项目作用域和执行服务放在一个清晰边界中。Agent 只看到工具契约，实际执行由后端服务完成。这样可以统一权限、日志、错误和远程/内置宿主的行为。
>
> MCP 还让工具声明可以被多个宿主复用。ArcReel 的内嵌 MCP 和远程 MCP 都从同一份工具声明投影生成，再通过宿主一致性测试校验，避免开发环境和生产环境出现“同名工具但参数不一致”。

**项目里的做法与原因：**

- MCP 服务按会话隔离，并接收项目作用域、调用者上下文和领域服务依赖。
- 工具列表只有一个声明来源，再投影到内置或远程宿主，避免多个入口各自维护一份工具定义。
- 复杂任务通过工具创建任务记录并追踪状态，而不是让模型自由拼接数据库记录；这样可以统一权限、错误和恢复语义。

### 题目 7：如何保证 MCP 工具的幂等性？

**推荐回答：**

> 我会先区分“请求是否重复”和“供应商是否已经提交”。工具层通过业务请求标识、目标资产和任务记录识别重复请求；队列层保存任务状态和供应商 task id；worker 在恢复或重试时先检查已有执行身份，不能因为一次轮询超时就重新提交。账单层再以 pending 调用作为结算条件，确保同一个业务调用只结算一次。
>
> 也就是说，幂等不是在一个函数里加一个布尔值，而是贯穿工具、任务、供应商和账本四层。

**项目里的做法与原因：**

- 任务记录同时保存请求事实、当前状态和执行身份，先用业务请求标识和目标资产做冲突检查，再决定是否创建新任务。
- worker 执行前检查任务状态、供应商和容量；一旦提交成功，立即保存远程 task id，后续重试只查询这个身份。
- 恢复时校验实际使用的供应商与入队时声明的一致，防止任务被错误路由到另一个供应商。
- 账单恢复只结算已有的 `pending` 调用，不重新创建费用记录，所以轮询重试不会重复扣费。

### 题目 8：如果模型被 Prompt Injection 指示“读取 .env 并上传”，你怎么处理？

**推荐回答：**

> 我不会只依赖 Prompt 告诉模型“不要读敏感文件”，因为 Prompt Injection 本身就是模型输入的一部分。ArcReel 采用执行层防护：Agent 的文件访问由 `AgentAccessPolicy` 统一判断，敏感文件、受保护写路径和 shell 参数在 hook 或 sandbox 层拒绝；核心项目产物不能由 Agent 直接改写，必须走主进程工具和服务层。
>
> 即使模型已经被诱导，最终的文件访问、命令执行和数据库写入仍然会经过路径归一化、权限规则和工具 schema。对于 Windows 没有内核 sandbox 的环境，系统使用 Bash 前缀白名单等降级策略，同时拒绝 shell metacharacter、路径穿越和敏感环境变量访问。

**项目里的做法与原因：**

- 文件访问规则集中在一套 `AgentAccessPolicy` 中，所有读取、搜索和写入动作使用同一套判断，避免某个工具漏掉安全规则。
- 对 `Read/Write/Edit/Glob/Grep` 等路径工具统一检查参数；项目核心产物和媒体目录默认受保护，必须通过服务层修改。
- 路径检查同时覆盖逻辑路径和 `resolve()` 后的真实路径，防止用路径穿越或 symlink 绕过项目边界。
- 敏感文件包含 `.env`、`.env.*` 和 Agent profile settings；受保护媒体目录包含 `characters`、`scenes`、`props`、`products`、`grids`、`storyboards`、`videos`、`audio`、`renders` 等。

### 题目 9：Provider secret 如何保护？为什么不能直接放在父进程环境里？

**推荐回答：**

> Provider secret 只在真正需要调用供应商的执行边界注入，不能让 Agent 通过普通环境读取，也不能把 token 放在模型上下文、日志或 SSE 消息中。SDK options 只接收当前调用需要的 secret，工具返回结果也只包含脱敏后的状态和输出信息。
>
> 这样做的原因是 Agent 运行时可能执行读取、搜索或 shell 工具；如果 secret 长期存在父进程环境，模型或误配置脚本就可能把它带出去。权限边界应该由宿主和服务层控制，而不是由模型自律。

**项目里的做法与原因：**

- 对敏感环境变量和读取路径做统一限制，避免模型借助普通读取工具拿到密钥。
- provider secret 不放在 Agent 父进程的常驻环境里，而是在真正调用供应商的执行边界通过 SDK options 或 adapter 注入；调用完成后不进入模型上下文。
- Agent 不允许直接拼 SQL 或绕过服务层写数据库，避免通过数据库读取配置表中的密钥。
- 日志和事件只记录 provider、模型、任务状态、错误分类和脱敏后的响应摘要。

## 4. 会话、流式响应与并发

### 题目 10：为什么要设计 `SessionActor`？直接给每个请求加锁不行吗？

**推荐回答：**

> 单纯给 HTTP 请求加锁不够，因为 Claude SDK 客户端不仅有 query，还有 interrupt、cancel、disconnect 和持续读取消息流。多个协程分别持有锁时，仍然容易出现“锁的生命周期和 SDK 流生命周期不一致”的问题。
>
> ArcReel 让每个会话只有一个 `SessionActor` task 持有一个 `ClaudeSDKClient`。HTTP/SSE 层只往 `asyncio.Queue[SessionCommand]` 投递命令；actor 在同一个 async context 中交替处理命令和 SDK frame。这样 query、interrupt、cancel、disconnect 都在同一个串行执行上下文中，SDK 的消息读取也不会和命令调用竞争。

**项目里的做法与原因：**

- 会话命令明确区分发送、打断、取消和断开，避免“取消一条消息”误伤整个会话。
- 一个消息泵持续读取 SDK frame，另一个命令循环负责接收用户命令；两者在同一个 Actor 中协调，因此不会有两个协程同时操作 SDK。
- 每条命令无论成功、异常还是 Actor 关闭，都必须返回完成结果；Actor 退出时会清理排队命令，避免 HTTP 调用方永久等待。

### 题目 11：`SessionActor` 如何处理 SDK 消息流结束？

**推荐回答：**

> SDK 的异步消息流结束不等于某一轮生成正常完成。`_MessagePump` 在 `StopAsyncIteration` 时抛出 `MessageStreamClosed`，actor 将这个事实通知会话层；`SessionManager` 再根据会话是否可恢复、是否已经有终态事件和当前 CLI 状态决定是关闭、标记错误还是保留恢复入口。
>
> 关键点是把“SDK 流关闭”“用户中断”“供应商任务完成”和“前端断开”分成不同事件，不能用一个布尔值表示所有情况。

**项目里的做法与原因：**

- SDK 消息流关闭有独立事件，和正常完成、用户中断、前端断开分开记录；这样恢复逻辑才能判断真正发生了什么。
- 命令排队、并入轮次、撤回等生命周期事件与模型文本消息分开处理，避免 UI 把内部状态误显示成内容。
- 会话管理器分别处理完成、错误、中断和关闭，并清理等待用户回答的问题。
- 会话断开不会直接把生成任务标记失败；生成任务由任务记录和 worker 状态决定。

### 题目 12：`EntryPipeline` 做了什么？为什么不让前端直接解析 SDK frame？

**推荐回答：**

> `EntryPipeline` 是 SDK 协议和产品事件之间的适配层。它负责归一化 SDK frame、累积流式 draft、写事件日志、处理特殊消息和终态。前端只消费稳定的产品事件，不需要知道 Claude SDK 的 frame 结构，也不会因为 SDK 协议变化而把解析逻辑散落在多个组件里。
>
> 流式展示和最终一致性是两条路径：增量 draft 用于让用户及时看到过程；终态和事件日志用于刷新、恢复和审计。即使浏览器中途断开，重新连接时也可以从持久化状态恢复，而不是依赖浏览器内存中的增量片段。

**项目里的做法与原因：**

- 入口管道先累积文本或结构化 draft，再把 SDK 消息归一化成产品事件；前端只依赖稳定的产品事件格式。
- 管道同时产出增量展示、事件日志和终态结果，把“实时看到过程”和“断线后恢复事实”分成两条路径。
- pending question 等特殊消息由会话层单独处理，避免普通文本解析逻辑误判。
- 特殊消息（例如 pending question）由会话层处理，不让普通文本消息路径误判。

### 题目 13：SSE 断线后如何恢复？为什么不能把 SSE 当成事实来源？

**推荐回答：**

> SSE 是实时展示通道，不是事实存储。服务端先把关键状态写入数据库、事件日志或任务记录，再广播 SSE。客户端断线后重新订阅，先拉当前项目和任务快照，再接收后续事件；如果事件流中间丢了非关键增量，也不会影响最终状态。
>
> 对生成任务尤其重要：SSE 断开只说明展示通道断了，不代表供应商任务失败。重连后应该查询任务状态和供应商 task id，而不是重新提交一个生成请求。

**项目里的做法与原因：**

- SSE 订阅支持空闲超时和心跳，客户端可以区分“暂时没有消息”和“连接已经失效”。
- 队列满时优先丢弃可重新计算的增量；关键终态消息尽量保留，如果仍无法容纳就结束订阅，让客户端重连并用快照对齐。
- 项目事件流允许直接移除慢消费者，因为它们可以通过快照恢复；这样一个卡住的浏览器不会拖慢其他订阅者。
- 首个订阅者到来和最后一个订阅者离开时可以启停后台扫描，避免无人观看时持续占用资源。

### 题目 14：SSE 如何处理慢消费者和背压？

**推荐回答：**

> 我会给每个订阅者有限大小的 asyncio 队列，并给消息定义关键级别。增量 token、心跳和可重新计算的进度属于非关键消息，可以丢弃；终态、错误、任务状态变化等关键消息必须尽量保留。如果关键消息遇到满队列，先淘汰一条非关键消息；如果队列里全是关键消息，继续发送已经没有意义，就结束该订阅，让客户端通过重连和快照恢复。
>
> 这样系统不会因为一个浏览器卡住而阻塞整个广播，也不会无限制地积压内存。

**项目里的做法与原因：**

- 每个订阅者拥有有限大小的队列，广播只把消息放入各自队列，不等待某个慢客户端消费。
- 消息带关键级别，增量、心跳和进度可丢弃，终态、错误和任务状态变化需要保留。
- 队列结束时发送内部结束信号，消费者可以正常退出，不会因为队列清空而永久阻塞。

### 题目 15：`interrupt`、`cancel`、`disconnect` 有什么区别？

**推荐回答：**

> `interrupt` 是中断当前正在处理的轮次；`cancel` 主要尝试从 CLI 队列撤回尚未开始处理的消息，如果 CLI 已经取走消息，撤回可能返回 false，但会话仍然可用；`disconnect` 是关闭会话，必要时先执行 interrupt。它们的语义不能混在一起，否则用户点“取消排队消息”可能把整个 Agent 会话关掉。
>
> 对供应商生成任务还要再区分一次：用户取消通常只作用于尚未提交给供应商的排队任务；已经提交的远程任务继续查询到终态，避免本地以为取消成功、远程仍然产生费用或素材。

**项目里的做法与原因：**

- 会话命令带有明确类型和“是否先打断”的选项，执行层再把它映射到 SDK 操作。
- 关闭会话时清理等待用户回答的问题，避免用户已经离开后仍有悬挂状态。
- 生成任务根据“尚未提交”或“已经拿到远程 task id”区分取消语义；后者继续查询终态，避免本地取消与远程实际执行不一致。

### 题目 16：如何避免同一个会话同时收到两条用户消息？

**推荐回答：**

> 我不在 HTTP 层假设“同一个会话只有一个请求”，而是在会话内部做串行化。多个请求都提交到 actor 的命令队列，actor 按顺序调用 SDK。CLI 自己会报告消息是排队、并入当前轮次还是被撤回，`SessionManager` 根据这些 lifecycle 事件更新状态和 UI。
>
> 如果产品要求禁止并发发送，还可以在会话层根据 CLI busy 状态拒绝新消息；如果产品允许排队，则保留消息 UUID，支持按 UUID 撤回和恢复。

**项目里的做法与原因：**

- 会话对象同时持有 Actor、订阅通道、状态、用量和排队消息，所有状态变化都从这个会话边界发出。
- CLI 空闲、忙碌、消息已结算等内部事件会转换成产品状态，前端看到的是“排队中、处理中、已完成”等稳定语义。
- 每条用户消息都有服务端 UUID，用于取消、重连后的对应和审计。

## 5. 生成队列、异步供应商与一致性

### 题目 17：图片、视频、音频生成为什么要拆成不同 lane？

**推荐回答：**

> 不同媒体的执行时间、并发限制、计费单位和失败语义差异很大。视频通常占用更长时间和更高成本，音频可能有独立的并发和时长计费，图片则更适合较高并发。统一一个无限队列会导致视频任务挤压其他任务，也无法按供应商能力做容量控制。
>
> ArcReel 把图片、视频、音频放到独立 lane/channel，再由 worker 根据 provider 和模型能力分配槽位。任务记录仍然统一，因此上层可以查询同一套状态和账单，但执行调度按媒体类型隔离。

**项目里的做法与原因：**

- 任务记录统一保存入队事实和状态，但执行按图片、视频、音频拆分 lane，避免长视频占满所有资源。
- 每个 provider 和模型都有容量槽位，worker 获取槽位后才提交请求，完成或失败时释放槽位。
- worker 执行前再次检查任务状态、provider、模型和容量，防止恢复扫描和正常消费同时拿到同一个任务。

### 题目 18：供应商 API 是异步的，如何避免提交后丢任务？

**推荐回答：**

> 提交供应商请求前，系统先创建本地任务并保存请求事实；供应商返回远程 task id 后，立即把 task id 写回任务记录。worker 后续只根据本地记录查询远程状态，不依赖当前进程内存。进程重启时，扫描处于执行中的任务，依据供应商 task id 恢复轮询或进入可恢复状态。
>
> 如果提交请求超时，不能直接判断“没有提交成功”。系统要结合供应商幂等键、请求事实和已有远程 task id 做判断；无法确认时宁愿进入人工或可重试状态，也不盲目重复提交高成本视频。

**项目里的做法与原因：**

- 本地任务在提交前创建，提交后立即保存 provider task id、错误、费用和输出路径；进程内存只负责当前执行，不能作为唯一记录。
- 独立 worker 负责提交、轮询、解析输出和完成任务，SSE 请求只负责展示，不承担长轮询。
- 任务记录保存可复现的请求事实和执行身份，重启后可以继续查询，而不是根据一段模型文本猜测是否提交过。

### 题目 19：如何处理“供应商已经成功，但本地回调超时”的场景？

**推荐回答：**

> 先把供应商任务成功和本地写入成功视为两个状态。worker 轮询到成功后，以供应商 task id 或本地 task id 做幂等更新，保存输出和 usage；如果保存响应超时，下一次恢复时仍然可以根据 task id 查询并重复执行“写入已存在结果”的幂等步骤。
>
> 账单结算也不能绑定一次 HTTP 响应，而要绑定持久化的调用记录。这样 worker 重试不会再次扣费，前端也能通过任务快照看到最终状态。

**项目里的做法与原因：**

- 恢复路径可以对已有调用结算，前提是调用仍处于 `pending`，这样本地响应超时后可以补齐结果。
- 通过 call id 或 task id 查找待结算调用，而不是每次恢复都创建新调用。
- 任务保存输出路径和供应商响应；重复处理前先检查是否已有终态，避免覆盖成不同结果。

### 题目 20：批量生成为什么要做请求前准入？

**推荐回答：**

> 批量视频最危险的是只创建了一半任务，或者用户在不清楚总时长和价格时意外提交。ArcReel 先对整批目标做预检，计算每个目标的时长、费用、模型支持情况和阻塞问题，再根据结果决定直接准入、需要确认还是阻止。
>
> 这是请求前准入，不代表执行一定成功。准入后每个任务仍然可能因为供应商、网络或内容审核失败，但至少不会出现“用户只确认了部分报价、系统已经创建另一半任务”的不一致。

**项目里的做法与原因：**

- 批量准入会为每个目标生成一张准入票据，记录问题、预计时长、预计费用和能力投影，先看清整批请求再决定是否创建任务。
- `ADMITTED` 表示可以直接创建，`CONFIRMATION_REQUIRED` 表示只差用户确认价格或时长，`BLOCKED` 表示存在能力、输入或安全问题；三者让 UI 能给出不同动作。
- 预检结果按币种汇总报价，并记录整批拒绝结果，避免用户看到半批成功、半批没有创建的模糊状态。
- 设计采用 all-or-nothing：整批预检完成后，要么创建完整任务集合，要么一个任务都不创建，原因是批量任务的部分创建很难撤销且容易造成费用误解。

### 题目 21：计费为什么要区分 `Priced` 和 `Unpriced`？

**推荐回答：**

> 未知价格不能默认为 0。否则新模型、未配置价格的供应商或缺少 usage 的任务会被误认为免费，最终账单和用户预估都会失真。ArcReel 的计量层把用量和价格分开：`Usage` 描述 token、图片张数、视频秒数、音频秒数等；`price_usage(...)` 根据价格表返回 `Priced` 或带原因的 `Unpriced`。
>
> 上层可以据此阻止需要确认的请求、显示“暂无法报价”，或者将任务标记为待补充价格，而不是偷偷使用另一个模型的价格。

**项目里的做法与原因：**

- 计量结果明确区分 `Priced` 和 `Unpriced`，未配置价格、缺少 usage、术语无法识别或无法估算时都返回具体原因，不把未知价格当成 0。
- token 计量覆盖输入、输出和缓存读写；媒体按图片张数、视频秒数和音频秒数计量；文本还支持 CJK 字符数，保证不同供应商可以映射到统一维度。
- 多次请求逐次计价再汇总，并保留币种信息；这样批量准入可以提前报价，实际结算也能解释差异。

### 题目 22：账单生命周期如何设计？如何避免恢复或重试重复扣费？

**推荐回答：**

> 账单不是接口返回时直接加一个数字，而是一个有状态的调用记录：开始时写 `pending`，成功时根据真实 usage 结算，异常转 `failed`，取消转 `cancelled`。恢复任务时只允许对符合条件的 pending 记录调用结算，因此同一个 call id 重试不会生成第二笔费用。
>
> 历史费用还需要冻结当时的价格和供应商响应，不能因为今天的价格表改变而重新计算过去账单。预估费用和实际费用分开，用户确认时显示报价，最终结算时以真实 usage 为准。

**项目里的做法与原因：**

- 调用开始先记录 `pending`，成功按真实 usage 结算，异常转 `failed`，取消转 `cancelled`；每个状态都有明确的业务含义和后续处理。
- 异步恢复只允许对已有 `pending` 调用结算，调用已经结束时再次恢复返回幂等结果。
- 用量、供应商响应、状态和调用关联都持久化，历史账单冻结当时价格，不能因价格表变化被重新计算。
- 计量负责“多少钱”，账本负责“这次调用走到哪一步”，分层后 worker 不需要自己拼接费用逻辑。

### 题目 23：生成任务、账单和 SSE 三者如何保持一致？

**推荐回答：**

> 我会把数据库中的任务和账单当作事实来源，把 SSE 当作通知。一次生成通常先创建任务和 pending 调用，再异步执行；worker 更新任务状态和账单，最后广播一个可丢失但可重放的事件。前端收到事件后刷新快照，而不是仅凭事件内容拼出完整项目状态。
>
> 如果任务更新成功但广播失败，重连后快照仍然能看到结果；如果广播先到但数据库还没提交，事件发布应该放在提交之后，或者由事件日志保证顺序。这样可以避免用户看到“成功”但刷新后又消失。

**项目里的做法与原因：**

- 任务和账单先落持久化存储，再由 worker 异步执行和更新；SSE 只负责把变化通知给订阅者。
- 广播失败不影响事实记录，重连时通过项目快照、任务查询和事件日志对齐；因此用户看到的 UI 可以短暂滞后，但不会把通知当成最终数据。
- Agent 对话事件保留会话上下文，项目事件强调实体失效和快照刷新，两类事件使用不同的恢复策略。

## 6. 供应商抽象与工作流扩展

### 题目 24：如何抽象不同的模型供应商？

**推荐回答：**

> 我会把产品需要的能力抽象成 `TextBackend`、`ImageBackend`、`VideoBackend`、`AudioBackend`，把供应商差异留在 adapter 和 capability 中。业务层关心“生成一张参考图”“生成 5 秒视频”“合成音频”，不直接依赖某个 SDK 的 response object。
>
> Adapter 负责参数转换、支持时长、参考图数量、同步或异步状态、错误分类、计费单位和输出解析。这样供应商 SDK 变化只影响 adapter，产品工作流和任务状态机不需要跟着重写。

**项目里的做法与原因：**

- 产品层只依赖统一的文本、图片、视频和音频能力接口，供应商差异留在 adapter 和 capability 中。
- worker 按统一任务协议调用具体 provider，并保存远程 task id；业务层不依赖某个 SDK 的 response object。
- 供应商倍率、模型倍率和价格表由计量层处理，adapter 只负责参数转换、状态查询和输出解析，不直接修改余额。
- UI 不直接调用供应商；业务服务不依赖供应商 SDK 返回对象；adapter 不决定产品工作流。

### 题目 25：如果要新增一个视频供应商，你会怎么做？

**推荐回答：**

> 我会先确认这个供应商的能力边界：支持的模型、时长、分辨率、参考图数量、同步或异步模式、任务查询和取消语义。然后注册 provider credentials、默认地址和模型目录，实现 `VideoBackend` adapter，把异常映射成统一错误类型，保存远程 task id，解析输出和 usage，接入价格表和设置页。
>
> 代码完成后要验证超时、提交后断线、重复提交、进程重启恢复、未定价和取消语义，不能只测一次成功响应。

**项目里的做法与原因：**

1. 在供应商注册表和模型目录登记能力、默认配置、支持的时长和分辨率，让准入阶段可以提前判断是否支持。
2. 实现统一 backend，业务层不直接依赖供应商 SDK 类型。
3. 在 worker 中同时处理同步和异步生命周期；异步提交后立即持久化 remote task id。
4. 把供应商错误映射为可重试、不可重试、需要用户修改输入等类别，决定后续动作。
5. 在价格表中配置计费维度和倍率，未配置时进入 `Unpriced`，不能默认为免费。
6. 接入设置、任务状态和输出解析，让用户能看到供应商差异被统一后的结果。
7. 验证成功、超时、断线、重启恢复、重复提交、未定价和取消，而不是只测一次成功响应。

### 题目 26：如果要增加一个新的工作流阶段，如何避免把逻辑塞进主 Agent？

**推荐回答：**

> 我会先定义这个阶段的输入、输出、前置条件、失败状态和用户确认点，再决定哪些部分是 Skill 或子 Agent 的推理，哪些部分必须是 MCP 工具和服务。阶段本身不应该直接修改多个领域表，而是通过领域服务生成可校验的中间结果，再由项目状态机记录阶段完成。
>
> 同时补齐恢复语义：如果阶段执行到一半进程重启，系统要能从任务和版本记录判断已经完成的单元，避免重复生成；如果用户修改了上游角色或剧本，要能标记下游资产过期并重新触发必要阶段。

**项目里的做法与原因：**

- 新阶段先定义输入、输出、前置条件、失败状态和用户确认点，再决定哪些是 Skill 或子 Agent 推理，哪些必须走确定性工具。
- 阶段状态、版本和资产关联由项目服务持久化，阶段本身不直接修改多个领域表，避免半完成状态无法恢复。
- 生成阶段复用现有任务队列、批量准入和账单生命周期，不在新 Skill 中复制一套执行和计费逻辑；这样新阶段仍然拥有统一的重试、恢复和审计语义。

### 题目 27：项目文件为什么需要版本历史和可回滚？

**推荐回答：**

> 创作项目不是一次性表单，用户会不断修改角色、剧本和分镜。如果 Agent 直接覆盖核心文件，生成错误后很难恢复，也无法解释某个镜头为什么发生变化。因此项目会保留快照或修订信息，把“当前状态”和“历史版本”分开。
>
> Agent 的写入应先生成结构化变更或通过服务提交，服务层校验后落盘；用户可以预览、接受、重做或回滚。媒体目录则由生成任务和版本关联管理，避免同名文件覆盖后丢失来源。

**项目里的做法与原因：**

- 项目快照带递增修订号，当前状态和历史状态分开保存；用户修改后可以知道哪个版本产生了某个镜头。
- 核心产物和媒体目录受保护，Agent 只能提交结构化变更或调用服务，避免直接覆盖用户手工修改。
- 生成任务记录输出路径、输入事实和版本关联，回滚时可以找到对应资产来源，而不是只剩一个文件名。
- schema 变更先考虑旧版本读取和迁移后的兼容性，避免 API、worker 和历史项目同时升级时丢失数据。

## 7. 前端状态、性能与可靠性

### 题目 28：前端如何避免多个刷新请求互相覆盖？

**推荐回答：**

> 我把项目刷新收敛到 Zustand 的 `refreshProject`，不让每个组件各自调用 `getProject`。同一时刻只允许一个请求执行，期间到达的请求合并为下一轮，使用最新项目名并合并 `invalidateKeys`。项目切换时轮换 `AbortController`，旧项目的迟到响应不能写回当前 store。
>
> 刷新失败保留旧数据并返回 `failed`，项目切换导致的主动取消返回 `cancelled`，不会把正常导航提示成网络错误。写操作完成后统一调用 `refreshAfterWrite`，由快照重新建立权威状态。

**项目里的做法与原因：**

- 项目状态层只有一个统一刷新协调器；它维护“当前是否刷新、是否排队、最新项目名、需要失效的实体和等待结果的调用方”。
- 同一时间只跑一个请求，期间的新请求合并成下一轮，避免多个组件同时拉取同一项目。
- 切换项目时轮换项目级 `AbortController`，写入前检查当前项目名和 `signal.aborted`，旧项目迟到响应直接丢弃。
- 测试覆盖刷新合并、项目切换取消和失败保留旧数据，确保优化不会破坏用户当前看到的内容。

### 题目 29：项目如何处理“事件到了但数据还没刷新完成”？

**推荐回答：**

> 事件只作为刷新触发器和用户反馈，不作为完整数据源。收到项目事件后，前端将相关实体加入 `invalidateKeys`，由 `refreshProject` 拉取项目快照并写入 store。如果多个事件在同一时间到达，只合并 key，避免重复请求。
>
> 对可以直接更新的轻量状态，可以先做乐观展示，但最终仍以服务端快照为准；如果刷新失败，保留旧数据并提示用户，而不是把旧数据清空造成闪烁。

**项目里的做法与原因：**

- 事件只携带“哪个实体可能变了”的提示，前端把实体 key 合并到失效集合，再由统一刷新协调器拉取权威快照；这样事件可以轻量、可丢失。
- 写入完成后统一触发刷新和提示，避免某个组件忘记更新相邻实体或继续使用旧引用。
- SSE 断线后通过项目快照、任务查询和事件重连恢复，不依赖丢失的增量事件。

### 题目 30：Agent 对话和项目事件为什么要分两类 SSE？

**推荐回答：**

> Agent 对话流关注消息、草稿、工具调用和会话生命周期；项目事件流关注资产、脚本、任务和项目快照变化。两者的消息频率、关键级别和恢复方式不同。对话流需要保留用户可见的上下文和 pending question，项目事件流更适合丢弃中间进度、重连后用快照对齐。
>
> 底层可以复用 `SseChannel`，但通过不同的消息分类和溢出策略表达业务差异，避免把两种语义硬塞进同一个事件格式。

**项目里的做法与原因：**

- 两类 SSE 复用同一套广播能力，但消息分类、关键级别和恢复策略不同：会话流保留对话上下文和 pending question，项目流允许丢中间进度。
- 会话流重点保证用户看到完整交互生命周期；项目流重点通知实体失效，客户端重连后先用快照对齐。
- 慢客户端可以被项目事件流移除，不影响其他订阅者，因为它能通过快照恢复。

### 题目 31：如果用户同时打开多个项目，如何避免数据串项目？

**推荐回答：**

> 服务端每个 Agent 会话和 MCP server 都绑定明确的 `ProjectScope`，工具不能用用户输入中的任意路径访问其他项目。前端 store 切换项目时轮换项目级取消域，旧项目在途请求即使返回，也会在写入前检查 `currentProjectName`，不符合就丢弃。
>
> 任务、事件和资产查询也带项目标识，不能只用一个全局任务 ID 推断当前页面内容。这样可以同时运行多个项目，又不会因为旧请求晚到覆盖当前项目。

**项目里的做法与原因：**

- 服务端会话和工具都绑定明确的项目作用域，文件访问同时检查工作目录、逻辑路径和真实解析路径。
- 前端切换项目时取消旧请求，并在写入前再次核对当前项目；即使旧请求晚到，也不能覆盖新项目状态。
- 任务、事件和资产查询都带项目标识，不能只凭全局任务 ID 推断当前页面内容。

### 题目 32：如何做容量规划和性能优化？

**推荐回答：**

> 我会先按资源瓶颈拆分：Agent 会话受 SDK/CLI 会话数限制，视频生成受供应商并发和费用限制，SSE 受订阅者数量和队列内存限制，数据库受事件和任务写入频率限制。然后针对每类资源设置容量表、超时、队列长度和指标，而不是笼统地加线程。
>
> 具体优化包括：不同媒体 lane 隔离；SSE 丢弃可重建的增量消息；前端合并刷新；事件日志按终态和关键事件持久化；worker 用 provider/model 的容量槽位控制并发。扩容前先确认供应商限流和数据库写入是否才是真正瓶颈。

**项目里的做法与原因：**

- Agent 会话、媒体生成、SSE 订阅和数据库写入分别有容量边界；worker 通过 provider/model 槽位控制并发，避免“加线程”掩盖供应商限流。
- SSE 使用有限队列和溢出策略限制慢消费者占用内存；前端合并刷新请求减少重复读取。
- 会话达到容量上限时快速拒绝或排队，不无限创建 SDK 会话；性能问题先按阶段指标定位，再决定扩容或改策略。

## 8. 安全、测试与运维

### 题目 33：如何测试一个 Agent 系统？只测 Prompt 结果够吗？

**推荐回答：**

> 不够。Prompt 结果只能覆盖一部分推理质量，Agent 系统还要测试工具契约、权限、会话生命周期、流式事件、任务恢复、幂等和费用。我的测试会把模型输出尽量固定或替换成 fake client，把不稳定的模型判断和稳定的状态机分开验证。
>
> 对于高风险链路，我会重点测“异常发生后还能否恢复”：SDK 流结束、SSE 队列满、供应商提交超时、worker 重启、重复回调、账单重复结算、前端项目切换和旧请求迟到。

**项目里的做法与原因：**

- 后端改动按影响范围运行单元测试和集成测试；Agent、SSE、任务恢复和接口契约不能只靠 Prompt 快照验证。
- 前端状态改动验证并发刷新、取消、项目切换和类型约束；关键用户链路再补端到端测试。
- 提交前按改动域执行统一闸门，确保测试、类型检查和构建结果一起通过。

### 题目 34：如何测试 SessionActor 的并发正确性？

**推荐回答：**

> 我会使用 fake `ClaudeSDKClient`，记录每次 `query`、`interrupt`、`cancel`、`disconnect` 的调用顺序，并让消息流在命令执行中间返回 frame。测试要验证：同一时刻不会有两个 SDK 协议调用并行；命令完成事件最终一定被触发；消息流关闭会通知会话层；actor 退出时排队命令不会永久等待。
>
> 另外要测取消边界：cancel 只撤回尚未被 CLI 取走的消息，撤回失败不会把会话标记为关闭；disconnect 在需要时先 interrupt。

**项目里的做法与原因：**

- 使用 fake SDK client 记录 query、interrupt、cancel 和 disconnect 的调用顺序，并在命令执行中间返回消息 frame。
- 用事件和 barrier 控制交错顺序，断言同一时刻不会有两个 SDK 协议调用并行，而不是只验证最终返回值。
- 模拟消息流提前结束，确认会话收到独立的流关闭事件；Actor 退出时确认排队命令都得到完成或关闭错误。

### 题目 35：如何测试供应商任务恢复和重复扣费？

**推荐回答：**

> 测试先创建一个已经保存 provider task id 的执行中任务和 pending ledger call，然后模拟 worker 重启。恢复 worker 应该查询已有 task id，而不是新建供应商任务；模拟供应商成功后，任务变成 succeeded，ledger 只生成一次 settled 记录。再次调用恢复入口，应该返回幂等结果，不新增费用。
>
> 另一个测试模拟提交请求超时：如果没有可靠的幂等键或 task id，就不能自动重提高成本任务，应进入可恢复或人工确认状态。

**项目里的做法与原因：**

- 测试先准备一个已保存 provider task id 的执行中任务和一个 `pending` 账单调用，再模拟 worker 重启。
- 恢复 worker 必须查询已有 task id，不能新建供应商任务；供应商成功后任务只结算一次，再次恢复返回幂等结果。
- 另测提交超时且没有可靠幂等身份的情况，确认系统进入可恢复或人工确认，而不是自动重复提交高成本任务。
- 同时断言输出路径和供应商响应不会被重复覆盖成不同结果。

### 题目 36：项目如何部署？数据库迁移和 worker 怎么配合？

**推荐回答：**

> Web/API、Agent Runtime、生成 worker 和前端静态资源可以按职责部署，但它们共享同一套项目、任务、事件和账单数据模型。数据库 schema 变更必须通过 Alembic 迁移，先保证旧版本服务可以读取，再逐步启用新字段，避免 worker 和 API 版本不一致时丢任务。
>
> worker 是可重启组件，所以任务状态和 provider task id 必须在数据库里；部署或重启时先恢复未终态任务，再处理新任务。监控上要区分 API 健康、Agent 会话健康、队列积压、供应商失败和账单未结算。

**项目里的做法与原因：**

- Web/API、Agent Runtime、生成 worker 和前端静态资源按职责部署，但共享同一套项目、任务、事件和账单事实。
- schema 变更先保证旧版本服务可读取，再逐步启用新字段，避免 API 和 worker 版本不一致时丢任务。
- worker 可随时重启，启动时扫描未终态任务并恢复；进程内队列只负责当前调度，不能作为唯一记录。
- 监控分别关注 API 健康、Agent 会话、队列积压、供应商失败和未结算账单，避免只看一个总健康状态。

### 题目 37：如何做可观测性？出了“生成很慢”你先看什么？

**推荐回答：**

> 我会先把端到端链路拆成几个时间段：请求进入和准入、任务入队等待、worker 获取槽位、供应商提交、远程执行、结果下载和本地落盘、账单结算、SSE 广播和前端刷新。每段都要带 project id、session id、generation task id、provider task id 和 call id，但不记录 secret 或完整用户内容。
>
> “生成很慢”可能是队列排队、provider 限流、供应商执行慢、下载慢或前端刷新合并造成的展示延迟。只有把这些阶段分开，才能决定扩 worker、调容量、改重试还是优化前端。

**项目里的做法与原因：**

- `SessionManager` 有会话状态、使用量和事件日志上下文。
- 生成任务记录 provider、模型、远程 task id、错误和输出路径。
- `Ledger` 记录调用状态和 provider response，便于把费用异常和任务异常关联。
- SSE 断线要记录订阅结束和重连，而不是把所有断开都记成生成失败。

## 9. 设计取舍与行为题

### 题目 38：为什么不让 Agent 直接写文件？这样不是更灵活吗？

**推荐回答：**

> 直接写文件确实灵活，但会破坏可校验性、版本性和恢复能力。Agent 可能写出不完整 JSON、覆盖用户手工修改、生成媒体路径不一致，或者通过路径穿越修改项目外文件。ArcReel 让 Agent 通过工具提交意图，由服务层校验 schema、项目范围和版本，再写入文件或数据库。
>
> 对创作体验来说，工具仍然可以提供“预览修改”“应用修改”“撤销修改”，所以用户得到的是可审核的灵活性，而不是不可追踪的任意写入。

**项目里的做法与原因：**

- Agent 的路径工具统一走访问策略，普通文件、核心产物和媒体目录有不同的读写规则。
- 访问判断同时检查归一化路径和 `resolve()` 后路径，避免路径穿越或 symlink 绕过。
- 项目核心文件和媒体目录由主进程工具、项目服务和版本记录写入，Agent 不直接打开数据库或覆盖正式产物。

### 题目 39：为什么不把所有状态都放在 Redis 或内存里？

**推荐回答：**

> 会话中的短期排队信息可以使用内存结构，但项目状态、生成任务、provider task id、事件日志和账单不能只放内存。Redis 或内存进程重启就会丢失，SSE 断线也无法恢复，更无法保证重复提交和费用结算的幂等。
>
> ArcReel 把内存用于 actor、订阅队列和当前刷新协调，把数据库用于可恢复事实。这样既能有低延迟的实时交互，也能在进程重启和浏览器重连后恢复。

**项目里的做法与原因：**

- 会话命令队列、SSE 订阅队列和当前刷新协调属于短期内存状态，断线后可以丢弃并重新订阅。
- 生成任务、provider task id、输出路径、事件日志和账单调用写入持久化存储，因为这些决定恢复、审计和收费。
- 会话会保存 SDK session id，支持恢复；关闭时清理 pending question，避免重启后留下悬挂交互。

### 题目 40：如果让你重新设计，会改进什么？

**推荐回答：**

> 我会优先加强三点。第一，为每类生成任务补全统一的状态机和幂等键，让提交、轮询、下载、落盘和结算的边界更明确。第二，建立更系统的故障注入测试，自动模拟 SSE 断线、SDK 流关闭、worker 重启、供应商超时和数据库提交失败。第三，完善可观测性，把会话、任务、供应商和账单串成一条 trace，缩短定位时间。
>
> 这些改进不会把 Agent 变成更大的 Prompt，而是继续把不确定性限制在推理边界，把执行、恢复和审计做成稳定的领域能力。

**项目里的做法与原因：**

- 我会把统一状态机和幂等边界补到任务提交、轮询、下载、落盘和结算的每一步，而不是只在 worker 外层重试。
- 故障注入围绕会话、SSE、供应商 task id 和账单恢复展开，自动模拟断线、流关闭、worker 重启和数据库提交失败。
- trace 关联字段可以沿用 session id、generation task id、provider task id 和 call id，避免只看单条日志。

### 题目 41：讲一个你会如何处理的线上故障。

**推荐回答：**

> 假设用户反馈“页面显示视频生成失败，但供应商后台已经有结果”。我会先用 project id、generation task id 和 provider task id 查任务记录，确认本地状态、远程状态和 ledger 状态是否一致；再看 worker 是否在供应商成功后落盘或结算阶段失败，以及 SSE 是否只是断开。
>
> 如果远程 task id 已存在，我不会重新提交任务，而是让恢复 worker 重新查询并执行幂等的结果落盘和账单结算。修复后通过项目快照和任务查询让前端恢复，最后补一个覆盖“供应商成功、本地响应超时、worker 重启后恢复”的回归测试。

**项目里的做法与原因：**

- 先查任务记录和 provider task id，确认本地任务、远程任务和账单是否处于同一阶段。
- 用调用 id 和待结算记录判断是否仍有 `pending` 费用；只要远程 task id 已存在，就让恢复 worker 查询，不重新提交。
- SSE 只负责通知；修复完成后由项目快照和任务查询恢复前端，不通过重放一条成功事件冒充事实。

### 题目 42：当模型输出不符合工具参数 schema 时怎么办？

**推荐回答：**

> 首先让工具层拒绝不合法参数，并返回机器可读的字段错误，而不是把错误 JSON 直接写入项目。主 Agent 可以根据错误提示修正一次；如果仍然失败，就把问题展示给用户或转为人工确认。对于会产生费用或批量任务的工具，参数校验必须发生在创建任务之前。
>
> 我会把“模型可以重试”与“业务可以重复执行”分开。模型修正参数可以重试，但如果任务已经创建，就必须使用原任务和幂等键查询，不能因为 schema 错误重新创建另一批任务。

**项目里的做法与原因：**

- MCP 工具参数在服务执行前先做 schema 校验，字段错误以机器可读形式返回给主 Agent。
- `BatchAdmission` 在批量任务创建前检查问题、价格和时长。
- `GenerationQueue` 和 `Ledger` 对已创建任务及 pending 调用提供恢复和幂等路径。

## 10. 面试收尾

### 20 秒项目总结

> ArcReel 是一个把文本和素材转成可编辑短视频的 Agent 平台。它的核心设计是让模型负责理解和编排，让 MCP、服务层和任务队列负责确定性执行，再用 `SessionActor`、SSE 背压、持久化任务、供应商 task id、重启恢复和幂等账单把长流程连接起来。这样系统既有 Agent 的灵活性，也具备生产系统需要的可审核、可恢复和可计费能力。
